# Flare Capability

English · [中文](README.zh-CN.md)

Flare IM **capability service**: the **Hook control plane** (configuration, validation, statistics and retention; hooks run in Message Ingest) + the **capability extension subsystem** (DDD: the `domain/capability` domain model and ports; CQRS: `application` contains only **`commands` / `handler` / `queries`**; infrastructure: under `infrastructure/capability`, split into **`registration` / `dispatch` / `routing`** packages). The process assembly entry point is **`composition`** (`process_config` / `runtime_context` / **`wiring`** / `bootstrap` / `hook_registry`; formerly `service`).

## Core responsibilities

- **Hook control plane**: writes and validates `hook_configs`, serves statistics and execution queries over `hook_executions`, and applies the retention period. See [Hook control plane](#hook-control-plane).
- **Capability extension**: aggregates resolvers via `CapabilityExtensionRegistry`; plugins are managed: the plugin registry holds their deployments, and the tenant's plugin projection authorizes them. Core knows no concrete plugin: calls, polls and the like are plugins built on business-neutral host capabilities. The capability catalog, authorization, and command dispatch are exposed via **`flare.capability.v1.CapabilityService` gRPC** on the same server as this process's hook port; external HTTP is forwarded to this gRPC by the access gateway (there is no legacy plugin host or outbox).

### Environment variables (capability extension)

| Variable | Description |
|------|------|
| `FLARE_PLUGIN_REALTIME_PUSH_URL` | Push Proxy `PushService` (`http(s)://` or `discovery://`) for the host capability `im.realtime.deliver`: a plugin's non-durable packet to the online connections of conversation members (unset: deliveries answer unavailable) |
| `FLARE_CAPABILITY_NOTICE_REDIS_URL` | Redis of the tenant notice channel `{namespace}:notice` (unset: the `token_store` profile, whose namespace also names the channel); after a newer plugin projection is committed Capability publishes `{"tenantId","kind":"plugin.catalog.changed","version"}` there and the gateways tell the tenant's connections |

### Capability gRPC (`CapabilityService`)

Consistent with `port` in `config/base.toml` (default **50051**); the client uses the `CapabilityServiceClient` generated by `flare-grpc-proto`. Main RPCs: `ListCapabilities`, `Dispatch`, `SetTenantCapabilitySwitch`. The `payload_json` of `Dispatch` is a JSON string, for example for `example.poll.vote`:

```json
{ "codec": "VP8" }
```

When the process is configured with **`database_url`**, the authorization / tenant switches of `CapabilityService` go through **`PostgresCapabilityPolicy`**, sharing a connection pool with the hook configuration; both the hook and capability tables live in the "Hook engine + Capability policy" section of **`deploy/init.sql`** (`hook_configs`, `hook_executions`, `capability_user_grants`, `capability_tenant_switches`, `capability_service_settings`, `capability_audit_log`, etc.; that section performs **`DROP TABLE IF EXISTS ... CASCADE` followed by `CREATE TABLE`** for all the aforementioned objects). If you get the error `relation "capability_service_settings" does not exist`, it means the table does not exist in the **PostgreSQL instance that flare-capability is currently connected to**: a common cause is that **the script ran against a different instance/database** (for example, the orchestrator uses `5432`, while the standalone process **`flare-capability` connects to `DATABASE_URL`, or else to the postgres profile of `[services.capability].postgres` (`[postgres.media]` when unset) in the loaded configuration; with neither it refuses to start** instead of falling back to a built-in connection string, see `composition/bootstrap.rs`). At startup a `flare_capability::db` log is printed (the redacted `host:port/dbname`); please align it with the target where `deploy/init.sql` is executed. **Note**: that section drops and recreates the Hook/Capability-related tables; for a production database, evaluate the data using a migration process. When no database is configured, **`InMemoryCapabilityGrants`** is used and development sample grants are injected.

### Plugin deployments

The operator registers a deployment in Core's plugin registry (`/platform/plugin-registry/**`); a process never registers itself. `ListRegisteredPlugins` reads the application's authorized snapshot and is diagnostics only.

### Plugin service calls (`plugin.service.dispatch`)

A plugin deployment calls a service that another installed plugin provides through the resource bridge, with its runtime credential (`x-flare-plugin-runtime`). Core admits the call against its local projection, the tenant's operation switches and the shared request budget. The router that verifies the service ticket and forwards the call lives in `flare-plugin-host`, which is not part of this open workspace, so the `flare-capability` binary built here refuses every service call like any denied resource request (and logs that at startup when plugin runtime keys are configured).

Release images, the development scripts and the plugin lab build `with-plugin-host/` instead: its own Cargo workspace that links the router and produces the same `flare-capability` binary (`cargo build --manifest-path flare-capability/with-plugin-host/Cargo.toml`). `scripts/start_server.sh` does this when `../flare-plugin-devkit` is checked out; `FLARE_CAPABILITY_PLUGIN_HOST=0` keeps the open build and `=1` requires the router.

### `ExtensionPlugin` identity

The `ExtensionPlugin` router (`flare.capability.v1.ExtensionPlugin/Call`) sits behind the signed-context layer with anonymous admission. The verified `x-flare-ctx` is the only identity: `GenericRequest.metadata`, `x-tenant-id`, `x-user-id` and similar caller metadata are never read.

- `flare.capability.v1.health_check` is the only operation answered without a context; an invalid context is refused with `UNAUTHENTICATED` even there.
- Every other operation needs a signed `User`, `Service` or `TenantAdmin` context: without one it is `UNAUTHENTICATED`. `Staff`, `System` and `Guest` contexts, and a tenant that is empty, `*` or padded with blanks, are `PERMISSION_DENIED`. Staff reach Core only through Admin Gateway.
- The handler receives the verified context, so tenant, user, actor, request id and trace id come from the signature. `flare.media.v1.list_plugin_routes` lists the signed tenant's plugins only; a `tenant_id` in its body must be empty or that tenant.
- Without a Cell key set (`FLARE_INTERNAL_CTX_PUBLIC_KEYS` / `FLARE_INTERNAL_CTX_PUBLIC_KEY`) the router is served without the layer and answers only the health check; every other call is `UNAUTHENTICATED`.

## Hook control plane

Hooks run in Message Ingest: `flare-im-hooks` is the one runtime, with the call chain, adapters,
circuit breakers, time limits and execution records. This service is the control plane and does not
run hooks, so a Capability outage does not affect sending.

Configuration lives in the `hook_configs` table (schema in `deploy/init.sql`). A row with a
`tenant_id` belongs to that application, a row without one is a platform hook. Hooks in the
deployment file are not here; Message Ingest writes a read-only summary of them to
`hook_deployment_summary`.

`CapabilityService.Administer` serves `flare.extension.v1.hook_config.*`: `create`, `get`, `list`,
`update`, `delete`, `set_status`, `get_statistics`, `query_executions`, `test`, plus
`flare.extension.v1.hook_point.list` and `hook_profile.list`. An empty `tenant_id` is the platform
scope, for platform staff with `core:hooks:platform:write`. Each write bumps the scope in
`hook_config_versions` in the same transaction, under an advisory lock so versions follow commit
order; Message Ingest polls it about once a second and reloads only what changed.

### Hook configuration item (`HookConfigItem`)

| Field | Meaning |
|---|---|
| `name` | Unique within application and hook type; platform and deployment names are reserved |
| `description` | Optional text |
| `enabled` | A disabled hook is not called |
| `order` | Position inside its source, 0 to 1000, lower first |
| `timeout_ms` | 1 to 30000; the runtime also caps it by what is left of the total budget |
| `require_success` | Required (`required` on the admin surface): a target failure answers a retryable 503. Otherwise the step is skipped |
| `selector` | `tenants`, `conversation_types`, `message_types`; empty matches everything |
| `transport` | gRPC (`endpoint` or `service_name`) or webhook (`endpoint`, `secret`, `headers`) |
| `metadata` | Passed to the hook as-is |

Signing secrets, webhook header values and gRPC metadata values are write-only. See
[Hook Plugin Contract](../docs/HOOK-PLUGIN-CONTRACT.md).

## Execution evidence

Message Ingest writes `hook_executions` in batches. Here:

- `hook_config.get_statistics`: execution counts weighted by `sample_weight`, average and p99 latency
  of the calls actually made, circuit open count and failures by error code.
- `hook_config.query_executions`: rows newest first, by time range, message id and success.
- A retention sweep deletes the oldest rows in batches.

| Setting | Environment | Default | Range |
|---|---|---|---|
| `hook_executions.retention_enabled` | `FLARE_CAPABILITY_HOOK_EXECUTIONS_RETENTION_ENABLED` | `true` | |
| `hook_executions.retention_days` | `FLARE_CAPABILITY_HOOK_EXECUTIONS_RETENTION_DAYS` | 7 | 1 to 90 |
| `hook_executions.retention_sweep_secs` | `FLARE_CAPABILITY_HOOK_EXECUTIONS_RETENTION_SWEEP_SECS` | 600 | 10 to 86400 |
| `hook_executions.retention_delete_batch` | `FLARE_CAPABILITY_HOOK_EXECUTIONS_RETENTION_DELETE_BATCH` | 5000 | 100 to 100000 |

The sampling, buffer and circuit breaker settings belong to Message Ingest:
`[hook_executions]` and `[hook_circuit]` in `config/services/message-ingest.toml`, and
`FLARE_HOOK_EXECUTIONS_*`, `FLARE_HOOK_CIRCUIT_*`.
